# 水都 — 治水・利水シミュレーション

侵食でつくられたリアルな流域を舞台に、**川と付き合いながら町を育てる**シミュレーションゲーム。
Cities: Skylines のようにセル単位で水が流れ、Timberborn のように水面から土が潤う。
梅雨と台風の増水をダムと堤防で抑え、渇水を貯水池と地下水で凌ぎ、田畑を潤して人口を養う。

シミュレーションは TypeScript のみ (ゲームエンジンなし)、描画は **three.js による 3D**。
地形・水面・施設・植生はすべて実行時に手続き的に生成していて、外部の 3D モデルや
テクスチャは一切持っていない。

**▶ ブラウザで遊ぶ: https://kamocyc.github.io/claude-web-test-14/**
(`main` へ push すると GitHub Actions がビルドして自動で更新される。WebGL2 が必要)

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # シミュレーションのテスト
npm run campaign   # 自動プレイヤーに2年ぶんプレイさせ、サンプルセーブを生成
npm run dam-effect # ダムあり/なしで同じ洪水を流し、治水効果を測る
npm run dam-sites  # ダムの適地 (谷の狭さ・流域・貯水量) を測る
npm run build      # 型チェック + 本番ビルド
```

`?seed=<数値または文字列>` を付けると同じ流域を再現できる (例: `/?seed=hydro-demo`)。
ゲーム内でも右下の**ルール**からシードを見たり、指定・ランダムで流域を作り直したりできる
(選んだシードは URL にも書き戻されるので、リロードすれば同じ流域が出る)。
ツールバーの**サンプル**を押すと、下の自動プレイヤーが育てた町 (人口1,404) をそのまま読み込める。

## シミュレーションのしくみ

### 1. 地形 — 水が削ってつくった谷

ノイズで骨格をつくったあと、実際に水滴を降らせて削る。

1. **ドメインワープした fBm + リッジノイズ** で山地 (北) から平野 (南) への骨格をつくる。
   格子ノイズは軸に沿った縞を生むので、オクターブごとに座標系を約 37° 回転させている
   (これをやらないと支流が不自然な平行線になる)。
2. **水滴侵食** を 9 万滴。慣性・運搬能力・堆積を持つ水滴が斜面を下りながら谷を刻む。
   侵食パラメータは 0..1 に正規化した高さ場を前提にしているので、メートルへの変換は侵食後に行う。
3. **Priority-Flood + ε** ([Barnes et al.](https://arxiv.org/abs/1511.04463)) で窪地を解消し、
   全セルからマップ外へ単調に下る経路を保証する。これで「水が溜まって消える」ことがなくなる。
4. **MFD (複数流向) の流域面積** を計算し、大きいところを河道として掘り込む。
   D8 (最急1方向) だと平坦地で流路が 8 方向に吸着して直線的な水路になるため、
   低い隣接セルすべてへ傾斜の 2.6 乗で按分している。
5. **山あいの狭窄部 (ゴルジュ) を彫る** — 流路が確定したあと、上流域の3つの帯で
   いちばん水を集めている地点を選び、**川筋をたどって両岸を河床 +21〜30m まで
   持ち上げる**。川そのものと支流は絶対に埋めないので、水の出口は塞がらない。
6. **下流域には逆に、幅の広い平らな氾濫原を彫る** — 川筋からの距離で目標高さを決め、
   **下げる方向にだけ**適用する。下流ほど (集める水が多いほど) 谷底を広く取る。

結果として、**分岐した支流・蛇行・河口の三角州・山あいの湖**が自然に現れる。

#### マップの南北構造 — 上流 1/3 と下流 2/3

マップは 2.3km 四方の切り出しで、**北の 1/3 が山地 (ダムを架ける上流域)、南の 2/3 が
平野 (人が住む下流域)** になるよう明示的に区分している。

この区分を成り立たせている要素は3つあり、どれが欠けても崩れる:

- **南北傾斜を尾根の振幅と同程度まで強くする**。弱いと起伏に埋もれて、シードによっては
  「起伏のある台地の南端に崖」という、山も平野も無い地形になる。
- **谷の軸 (南北に蛇行する本流の通り道) を置く**。傾斜を強くするだけだと、斜面を平行に
  流れ落ちる小川が十数本並ぶだけになり、「一本の川の流域」に見えなくなる。軸から
  離れるほど地面を持ち上げて、支流が本流へ集まるようにしている。
- **狭窄部を上流域だけに閉じ込め、下流には氾濫原を彫る**。

#### なぜ狭窄部と氾濫原の両方が要るのか

狭窄部は**ダムを架けられる場所をつくる**ため。ダムはセルごとに 1 基 (￥4,200) 並べて谷を
塞ぐので、必要な径間数がそのまま建設費になる。`npm run dam-sites` で測れる。

氾濫原は逆に、**洪水に広がる場所を与える**ため。谷が細いままだと、水位が上がっても水は
谷の中で深くなるだけで横に広がらない。実測では日雨量 720mm でも浸水は陸地の 3.8% に
とどまり、そのかわり水深が 9.5m に達していた — 峡谷の底がいくら深くなっても、段丘の上の
町には何も起きないので、堤防にも排水機場にも仕事が生まれない。

ダムの位置には**両側からの制約**があり、山地の出口 (ちょうど 1/3 の境) に落ち着く:

- 上流に寄せすぎる → 集水する前の細い沢しか塞げず、ダムが支配する流域が 20% → 8% に落ちる。
- 下流に寄せすぎる → 人が住む氾濫原を峡谷が潰す。

また狭窄部は**背水長より長く**なければならない。上流域の河床勾配は約 0.53m/セルなので
16m の堰がつくる背水は約 30 セル伸びる。峡谷がそれより短いと貯水池の上流端が壁の外へ
はみ出す。壁を河道沿いの細い縁にするのも同じ理由で駄目で、せき止めた水が縁の外側
(隣の支流の谷) へ乗り越え、そのまま下流の平野へ抜けてしまう。峡谷を囲む**山塊**に
なるまで広げて、周りの分水嶺ごと持ち上げている。

#### 結果

`npm run dam-sites` — 全6シードで「16m の堰を 10 径間以内で架けられて、貯水池がマップ内に
収まる」地点が確保できている。

| | 南北を区分する前 | いま |
|---|---|---|
| 10 径間以下で架けられる地点 | 0〜3 箇所 (6シード中5つが 0) | **7〜82 箇所** (全シード) |
| 本流を塞ぐ最小径間 (seed hydro-demo) | 12 径間 ￥50,400 | **7 径間 ￥29,400** |
| その地点が押さえる流域 | — | 全流域の **20%** |
| ダムの位置 | 町のすぐ隣 (南 80〜90%) | **山地の出口 (北 20〜50%)** |

洪水の広がりかた (seed `hydro-demo`, 25mm/h × 18時間 = 日雨量 450mm)。
**山では深く狭く、平野では浅く広く**という、沖積河川の挙動になっている。

| 帯 (北→南) | 浸水面積 | 最大水深 | |
|---|---|---|---|
| 10-40% (山地) | 0.9〜1.9 ha | 4.6〜8.8m | 峡谷の天然の湖 |
| 50-100% (平野) | 1.5〜2.7 ha | 1.3〜2.2m | 氾濫原の湛水 |

平野側の 1.3〜2.2m は住宅の耐水深 (0.32m) を大きく超えるので、**堤防・排水機場に初めて
仕事が生まれる**。区分する前は、同じ雨で浸水は陸地の 2.0% にとどまり、そのかわり水深が
8m に達していた — 峡谷の底が深くなるだけで、段丘の上の町には何も起きなかった。

雨に対する反応の幅も広がった (氾濫面積 日雨量120mm → 720mm):

| | 南北を区分する前 | いま |
|---|---|---|
| 氾濫面積の伸び | 3.1 ha → 18.5 ha (**6倍**) | 1.3 ha → 19.0 ha (**15倍**) |
| 氾濫ピークの時刻 | 雨が止まって 12〜94時間後 | **降雨中〜直後** (h=20〜27) |

「晴れているのに数日後にいちばん水が来る」という挙動が消えたのは、水が氾濫原へ
横に広がれるようになり、細い谷に閉じ込められて溜まらなくなったため。

### 2. 水 — 仮想パイプ法による浅水シミュレーション

`src/sim/hydrology.ts`。セル間に仮想のパイプを張り、水面標高差で流束を加速、摩擦で減衰させる
(Mei et al. のモデル)。

- 流束は符号付きで辺ごとに 1 本だけ保持し、**そのセルにある水量以上は流出できない**制約で
  スケールする。これで水深が負にならず、質量が厳密に保存される
  (テスト: 盆地に入れた水は総量を保ったまま水平な水面に落ち着く)。
- 構造物 (堤防・ダム・水門) は地形を嵩上げした「壁」として扱う。だから水は物理的に堰き止められ、
  水位が天端を越えれば普通に**越流する**。
- マップ外は海 (標高 0m) として扱い、境界から水が出入りする。

### 3. 時間 — 圧縮された河川時間

このマップは全長 2.3km、河川の一区間にすぎない。上流の広大な流域はマップ外にあるので、
洪水の主因は**源流セルからの流入量 (m³/s)** として与える。

水理計算はゲーム時間とは別の時計 (hydro-sec) で回る。1 ゲーム時間 = 72 hydro-sec。
「1時間あたり◯mm」で与えられる降雨や地下水流出を流量に直すときは 3600 で割り、
河川流量と同じ物差しに乗せる (`TIME_COMPRESSION`)。
この換算を間違えると、**川が受け取る量より蒸発・浸透で失う量が大きくなって数日で干上がる** —
実際に開発中に一度そうなった。

### 4. 灌漑 — Timberborn 方式の湿潤伝播

`src/sim/moisture.ts`。水面 (川・水路・湛水) を水源としたバケットキュー BFS で、

- 最大 **11 セル**まで湿潤が広がり、距離に応じて減衰する
- ただし**水面より 2.6m 以上高い土地へは登れない**

段丘の上の畑を潤すには、水路を掘って水を引くか、水門で水位を上げる必要がある。
土壌水分も湿りを与えるので、雨のあとは一時的に畑が作れるが、乾けば枯れる。
安定した農業には灌漑が要る。

### 5. 気象 — 予報が嘘をつかない天気

`src/sim/weather.ts`。**その日の天気は「日番号とシードから決まる純関数」**なので、
7日先の予報は必ず当たる。プレイヤーは予報を信じて備えられる。

1年は 96 日で、春 → 梅雨 → 夏 → 秋 → 冬。梅雨は雨が多く、夏〜秋にはまれに**台風** (日雨量 150〜340mm)。

降った雨はマップ外の流域に貯まり、**速い応答 (時定数 9h) と遅い応答 (520h)** の 2 段の
貯留槽を通って流入量になる。だから雨が降ってから川が増えるまでに数時間〜数日の遅れがあり、
雨が止んだあともしばらく増水が続き、降らない日が続くと緩やかに渇水へ向かう。

実測 (1年通し): 冬の渇水期 約 5 m³/s、平水 10〜20 m³/s、梅雨の大雨で 130 m³/s。

**手動天気モード** — 画面下の「天気」から、暦を無視して降水強度 (mm/h)・天気・気温を
好きなタイミングで指定できる。解除するまでその天気が降り続けるので、梅雨や台風を待たずに
洪水を試したり、晴れを続けて渇水を起こしたりできる。
指定した雨はマップ外の流域貯留にもそのまま入るので、**流入量は普段と同じ経路で数時間遅れて
増える** (堤防やダムの効きを試すのに使える)。手動のあいだは予報も「この天気が続く」を返し、
無降雨日数は実際に降った量から数える。セーブにも残る。

### 6. 都市・農業・経済

- **上水道**: 取水施設 → 浄水場 → 配水池 → 水道管 → 住宅。水道管でつながっていない住宅には
  給水されない。処理能力を超えた原水は未処理水として配られ、満足度が下がる。
  川が涸れれば取水量は落ち、配水池の貯留を取り崩す。
- **農業**: 畑は湿潤度 35%、水田は 80% を要求する。水田は収量が高く浅い湛水にも耐える。
  冠水すれば作物は傷む。
- **人口**: 給水・食料・浸水しない立地の 3 つが揃った住宅に人が入る。税収が財源。

### 7. 災害

- 堤防やダムは**越流すると損傷し、健全度 0 で決壊する**。決壊すると壁が消えて一気に浸水する。
  ただ高くするだけでは守れない。
- 建物は水深が耐性を超えると損傷して失われる。耐性は施設ごとに違い、取水施設は水中でも平気、
  水道管は埋設なので強く、住宅は 32cm で浸水被害が始まる。
- **排水機場**は半径 6 セルの内水を強制排除する。堤防の内側に溜まった水を汲み出す最後の砦。
- 「氾濫面積」は平常時の水域との差で測る。ダムで貯めた水のように 3 日以上ずっと
  水を湛えている場所は新しい水域として平常時に繰り入れ、洪水と区別する。

## 描画 — three.js による 3D

「どこが高くて、どこに水が来て、何が建っているか」が一目で分かることを目標にしている。
モデルもテクスチャも外部ファイルを持たず、すべて起動時にコードから作る。

### 地形

> 既定は下の「ボクセル (ブロック) 表示」。ここで説明するのは、画質パネルで
> ブロック表示を切ったときのなめらかな地形で、ボクセル側も色分けはこれを流用している。

頂点は等間隔の格子 (セルあたり 2 分割 = 384×384) で、**標高は頂点シェーダが標高テクスチャから読んで
持ち上げる**。だから掘削・盛土のたびに 15 万頂点を CPU で作り直さずに済み、更新は
192×192 のテクスチャを1枚書き換えるだけで終わる。

法線はフラグメントシェーダで標高テクスチャの差分から作る。ポリゴンの分割数に縛られないので、
遠景でも尾根と谷が潰れない。ここに「谷は暗く尾根は明るく」する曲率項を足していて、
これが起伏の読み取りやすさにいちばん効いている。

地表の色は**標高・傾斜・流域面積・水深・湿潤度**から手続き的に決める。

| | |
|---|---|
| 砂利・砂 | 汀線と河床 (流域面積が大きいところ) |
| 草地 → 森 | 標高 6〜26m で入れ替わる。マクロノイズで斑にする |
| 岩 | 傾斜が急なところ。三面投影 (triplanar) でテクスチャが伸びないようにする |
| 雪 | 雪線より上。冬は雪線が下がる |
| 濡れ | 水深と土壌水分で暗く・つやを出す |

浮動小数テクスチャは WebGL2 では線形補間できないので、シェーダ側で自前のバイリニア補間をしている
(水面標高は cm 単位の精度が要るため half-float では足りない)。

### 水面

> こちらも既定はブロック表示。波・フレネル・泡の作りはブロック表示でも同じものを使う。

地形と同じ格子を**水面標高**まで持ち上げる。乾いたセルでは水面標高 = 地面標高なので、
水際では水面が自然に地面へ潜り込む (別途マスクを作らなくても汀線が出る)。

法線は「水面そのものの傾き」+「流速方向へスクロールする波の法線マップ2枚」。
だから**急流では水面が傾いて波が下流へ流れ、湖ではゆっくり揺れるだけ**という差が出る。
深さで吸収した透過色と、フレネルで混ぜた空の反射、太陽のハイライト、
早瀬と汀線の泡を重ねている。空の色は天球と同じ関数から作っているので、夕焼けは川面にも映る。

**遠景では反射を意図的に弱めている。** 引いて見ると視線が水面をかすめるため、
物理どおりに計算するとフレネルがどこも 1 に近づき、川面が一様な「空の鏡」になって
水の広がりも川底の地形も読めなくなる。さらに 1 ピクセルに波が何本も入るので、
太陽のハイライトがちらつき、ブルームで増幅されて白く飛ぶ。そこで視距離
260m→1100m でフレネルの上限を 0.78→0.34 に、鏡面反射を 22% まで落としている。
物理的な正しさより、**引いた画で地形と水が見分けられること**を優先した判断。

### ボクセル (ブロック) 表示

既定では地形を **3m 立方のブロックの積み重ね**として描く (Timberborn 風)。
画質パネルの「ブロック表示」で、従来のなめらかな地形にいつでも戻せる。

**丸めているのは表示だけで、シミュレーションは連続標高のまま回っている。**
`World.height` は変えていないので、水の挙動・氾濫判定・灌漑・建設可否は
なめらか表示のときと 1 ミリも変わらない。丸めは `voxelH()` (`src/config.ts`) の
1 箇所だけで定義し、GLSL 側 (`VOXEL_GLSL`) がまったく同じ式を持つ。
`Math.round(x)` と `floor(x + 0.5)` は負の標高でも一致するので、木や建物が
ブロックから浮くことはない (`tests/voxel.test.ts` が全域で突き合わせている)。

#### ジオメトリ — 境界面は1枚ずつ

「セルごとの上面」+「セル境界ごとの垂直な面」でできている。垂直面は
**境界1つにつき1枚**しか置かず、どちら側のセルが高いかは頂点シェーダで決める
(高いほうが面を持ち、法線の符号もそちら向きに合わせる)。セルごとに4枚張るより
4 割ほど三角形が少なく、**なめらか表示より軽い**。

| | 頂点 | 三角形 |
|---|---|---|
| なめらか (分割 2) | 148,225 | 294,912 |
| ブロック | 443,904 | **221,952** |

Y は毎フレーム頂点シェーダが標高テクスチャから読むので、掘削・盛土しても
ジオメトリは組み直さない (なめらか表示と同じ利点)。マップ外を指す外周の境界面は
−24m まで落としてあり、そのままジオラマの側面になる。

巻き順は頂点シェーダで変えられないため、マテリアルは両面描画。裏面は必ず地形に隠れる。

#### 立方体に見せる工夫

1 セル内の 16 ブロックは同じ高さなので、**4×4 に細分するジオメトリは要らない**。
目地はフラグメントシェーダでワールド座標から引き、ブロックごとの色ムラと
縁の面取りの陰を足すと立方体に見える。

問題は**高さ強調**で、既定の 1.45 倍だと 3m のブロックが画面上 4.35m の高さになり、
目地を 3m 間隔で引くと縦長のレンガになってしまう。そこで
**目地の間隔を1段の見かけの高さに合わせる** (`voxelBlocksPerCell()`)。

| 高さ強調 | 1セルあたり | 目地 | 縦横比 |
|---|---|---|---|
| 1.00× | 4×4 | 3m | 1.00 |
| 1.45× (既定) | 3×3 | 4m | 1.09 |
| 2.00× | 2×2 | 6m | 1.00 |
| 3.00× | 1×1 | 12m | 0.75 |

ブロック数は整数しか取れないので比をぴったり 1 にはできないが、比で近いほうを選ぶので
**スライダをどこに動かしても √2 倍以内**に収まり、かつ目地がセル境界と必ず揃う。

色分けの判定 (草・岩・雪・砂利) には**丸める前の標高**を使う。丸めた標高で見ると、
段差の隣り合うブロックで傾斜が 0 と 3m を往復し、岩と草が1ブロックごとにちらつく。
崖の側面は絶対標高で帯を引くので、隣り合う柱で地層が水平につながる。

なお画面空間パターン (目地・格子線) を「セル座標の `fwidth`」から作ってはいけない。
面の上でセル座標が定数になるので微分が 0 になり、セル全体が点いたり消えたりする。
ワールド座標から作ること。

#### 水も段差状に

水面も同じトポロジで、**セルごとに平らな水面 + 水際に垂直な壁**を立てる
(Timberborn の「水ブロック」)。**水深そのものは連続値のまま**で、垂直方向に
量子化はしない。0.2m の水たまりは 0.2m の高さで描かれるので、浸水判定
(`FLOOD_DAMAGE_DEPTH = 0.32m`) と見た目がずれない。

壁の下端は `max(両セルの河床, 低いほうの水面)` で決める。こうすると水中どうしの
境界では壁が潰れて**湖の中に板が立たず**、水際では自セルの河床で止まる
(そこから下は地形が描く)。

ひとつ落とし穴がある。地形を丸め**上げた**セルでは、素の `solid + water` が
ブロック上面より下に来てしまい、**水がブロックの中に埋もれて消える**。
実測でおよそ 2 割の水面セルがこれに当たったので、水面は必ずブロック上面より
上に出すようにしている (`voxelLevel()`)。

水面の法線は、なめらか版の「水面そのものの傾き」がセルごとに平らだと使えないので、
平らな面に波だけを乗せる。壁のほうは波を下向きにスクロールさせ、上端 (落ち口) を
白くしているので、段差がそのまま滝に見える。

#### 表示だけ丸めることの割り切り

ブロック上面は `World.height` から最大 ±1.5m ずれる。したがって
**汀線がブロックの目地の上に必ず乗るわけではない** — 崖の途中で水位が切れる。
建物・木・カーソル・画面からのピックはすべて丸めた高さに合わせてあるので浮き沈みしないが、
「地形データそのものを格子に丸める」ところまでは踏み込んでいない
(踏み込むと灌漑・建設判定・地形生成の作り直しが要る。下記「水の挙動」を参照)。

なお注視点の高さだけは**連続標高のまま**にしてある。ここを段差にすると横移動のたびに
注視点が段を上下して画面が揺れる (`tests/camera.test.ts` が数値で押さえている)。
段差を使うのは画面からのピックだけ。

#### 水の挙動は Timberborn とどう違うか

**表示だけ丸めている現状では、水の挙動は一切変わっていない** (`Hydrology.step()` に触れていない)。
そのうえで、このシミュレーションと Timberborn の水を比べるとこうなる。

意外にも**中核は同じ系統**だった。Timberborn も各タイルが4近傍と「仮想パイプ」で
繋がり、タイルごとに水深値を持ち、水位を均そうとする。流れの向き・強さ (current) は
ティック間に動いた水量から出す派生量で、ここも本プロジェクトが流束から `vx/vy` を
作っているのと同じ。**水深が連続値**なのも同じで、Timberborn でもボクセルなのは地形だけ。

違うのは次の点。

| | 水都 | Timberborn |
|---|---|---|
| 垂直の水層 | **1セル1水面 (2.5D)** | Update 6 (2024/10) で 3D 化。**水が縦に複数層** — 建物の上を流れる、水中トンネル、オーバーハング |
| 慣性 | **あり**。`fR[i] = fR[i]*DAMPING + accel*Δ水位` は流束に慣性を持つので、段波・振り戻し・ダム決壊の波front が出る | レート制限付きの水位平準化が主。水はもっと素直で早く落ち着く |
| 時間 | 1ゲーム時間 = 36ステップ × 2 hydro-sec の**圧縮時間軸** | 数百 ms/tick の実時間 |
| 水以外の水文 | **蒸発・浸透・土壌水分ストック・地下水 (基底流出)** まである | 蒸発と水源出力の変動が中心。地下水の概念は無い |
| 汚染水 | 無い | badwater がある |
| 地形改変 | 連続値で掘削・盛土 | **ブロック単位**で自由に掘削・盛土 |
| スケール | 1セル 12m / ブロック 3m | 1タイル 1m / ブロック 1m |

いちばん大きいのは**垂直の水層**。ここは 2.5D のハイトフィールドなので、見た目を
ボクセルにしてもオーバーハングも洞窟も水の重ね合わせも作れない。「見た目はブロック、
データは柱1本」で、これはデータモデルを作り直さないかぎり変わらない。

次に効くのが**慣性**。ブロック表示にすると段差の縁で慣性のある水が一段ずつ跳ねるので、
Timberborn より暴れて見える。落ち着かせたいなら `HYDRO.DAMPING` (現在 0.9) を下げる
チューニングが要る。

#### 地形データまで丸めたら、挙動はこう変わる (未実装)

`VOXEL.quantizeTerrainData` は用意してあるが、まだ効かない。有効にするなら
少なくとも次の手当てが要る — つまり**表示だけのボクセル化とは別物の作業**になる。

1. **段差が堰になる (Timberborn に近づく)。** 平らなテラス上では隣接セルの地面差が 0 に
   なり、駆動力が水深差だけになる → 浅い水は鈍くなり「面で溜まる」。段の縁では一気に
   落ちる。「一段ずつ満たしてから越流する」挙動そのものになる。
2. **細い流路が消える。** 河道の掘り込みは 1.15〜9.5m なので、3m 格子では浅い支流が
   丸めで消える。→ 丸めた後に河道を1ブロック掘り直す処理が必須。
3. **窪地が新しくできる。** `resolveDepressions()` が保証している「全セルが海まで単調に
   下る」性質が丸めで壊れる (`tests/terrain.test.ts` の `countPits === 0` が落ちる)。
   → 丸めた後に `resolveDepressions` を再実行する。
4. **灌漑が壊れる。** `IRRIGATION.CLIMB = 2.6m` は 3m ブロック1段より低い。丸めると
   **水面から一段上がった土地へは湿潤が一切届かなくなり**、川と同じテラスにしか農地を
   作れなくなる。CLIMB を1ブロック分以上へ上げる必要がある。
5. **建設可否が二極化する。** 傾斜判定はテラス内なら 0、段の縁なら 1.5〜3.0。`maxSlope` は
   0.85 (水田) 〜3.5 なので、「テラス内はどこでも可 / 縁は不可」に分かれる。
6. 氾濫原 (標高 0〜10m) が 3〜4 段に潰れるので、同梱セーブ・自動プレイの数値も作り直し。

### 空・光

ゲーム内時刻から太陽の方向を決め、その高度で空の色 (天頂・地平・太陽) を作る。
**その空から PMREM で環境マップを焼いて `scene.environment` に入れている**ので、
地形も建物も「空の色で」照らされる。天気に応じて雲量・減光・霧の濃さが変わり、
雨や雪はカメラ周りの箱を落ち続ける GPU パーティクルで降る。

**雨のとき、画面を青くしすぎない。** 雨粒 (9000 点) は画面全体に重なるので、
濃い青みをつけると地表が青いベールに覆われて何も見えなくなる。粒は薄く中間色にし、
霧も雨量で濃くしすぎない (40mm/h で密度 0.00145 → 0.00084)。地表の「濡れ」も
実際に水がある所 (水たまり・潤った土) と「降っているあいだの湿り」を分け、
**青みは水がある所だけ**、雨はわずかに落ち着いた色になる程度にとどめている。

影はマップ全体を覆う位置に固定した平行光源のシャドウマップで落とす。
視点に追従させて範囲を絞ると、シャドウマップの外側が「常に影」と判定されて遠景が
一様に暗くなってしまうため。

### 施設・植生

施設は箱・円柱・角錐の組み合わせで、種類 × パートごとに `InstancedMesh` を1つ持ち、
毎フレーム行列と色を書き込む。シミュレーションの状態がそのまま見た目に出る:

- 作物は**生育度で背が伸びて色が緑 → 黄金色**に変わる
- ゲートは**開けると持ち上がり**、水が抜ける隙間が見える
- 損傷した堤防・ダムは**実際に低くなる** (`World.effectiveWall` と同じ係数で縮む)
- 夜は住宅の窓が灯る (入居している町だけが光る)

樹木は「急すぎる崖・河床・雪線より上には生えない」という規則で撒き、
低周波ノイズで森の疎密を作る。建物を建てるとその区画の木は消える。

### 高さ方向の強調

このマップは 2.3km 四方に対して比高が 130m しかなく、実寸で描くと平らに見える。
そこで既定で **1.45 倍**に強調している (画質パネルで 1.0〜3.0 倍に変更可)。

ただし強調するのは**地形・水面・堤防・ダム・水門**だけで、住宅や浄水場の高さは実寸のまま。
建物まで伸ばすと家が塔のようになってしまう一方、堰の高さは「水を止める高さ」そのものなので、
水面と同じ倍率で伸ばさないと嘘になる。

### カメラ — 地形を「均した面」の上を滑る

注視点は地面の上に乗せているが、その高さに**生の標高をそのまま使うと横移動が揺れる**。
小さな谷や畝を1つ越えるだけで注視点が上下し、既定の高さ強調 1.45 倍がそれを増幅するため、
移動中は画面ががくがく揺さぶられていた (実測で 1 フレームあたり最大 16m)。

対策は 2 段:

1. **空間的に均す** — 注視点の高さは 1 点ではなく、周囲 13 点の加重平均で決める。半径は
   カメラ距離の 0.22 倍 (最大 20 セル) なので、寄れば地形に沿い、引くほど大づかみになる。
2. **時間的に均す** — 求めた高さへ時定数 0.16 秒で追従させる。尾根を越えるときも一拍おいて
   追いつく。

結果、1 フレームの上下動は最大 16.5m → 1.3m、平均 0.81m → 0.28m に下がり、それでいて
横断したときの全体の高低差は 101m → 82m と、大きな起伏には従来どおり乗る
(`tests/camera.test.ts` が数値で押さえている)。なお画面 → セルの変換 (ピック) には
均していない生の標高を使う。均した面で当たり判定をすると、掴んだ地面がカーソルからずれる。

## 自動プレイヤーによる検証

「このゲームは実際にクリアできるのか」を人手で確かめるのは大変なので、
機械的にプレイする自動プレイヤー (`tools/autoplay.ts`) を用意し、
何もない流域から 2 年ぶん通しでプレイさせている (`npm run campaign`)。

自動プレイヤーは毎日こう判断する:

1. **給水能力を人口に先行させる** — 需要の 1.8 倍を保つように取水・浄水・配水池を増設
2. **食料は「在庫」ではなく「生産能力」で判断** — 人口比の在庫を目標にすると農地が際限なく増えて維持費で潰れる
3. **治水は町が稼げるようになってから** — 人口 500 を超えたら積立を始め、堤防 → 排水機場 → ダムの順に固める
4. **拡張が収支の柱** — 住宅は 10 日ほどで元が取れるので、積立を上回った分はすべて宅地に回す
5. **ゲート操作** — 予報のピークが 55 m³/s を超えれば事前放流、出水中は絞ってピークカット、
   ただし上流水位が天端まで 2.5m を切ったら全開 (実際のダムの「ただし書き操作」)

### 結果 (シード `hydro-demo`, 192日)

| | |
|---|---|
| 人口 | 43 → **3,168 人** |
| 給水率 | 常に **100%** |
| 運転収支 | **+494 ￥/h** (黒字で安定) |
| 最大流入量 | **374 m³/s** (台風) |
| 失った建物 | 19 (氾濫原の水田×14 畑×5) — **住宅・上水道・治水施設は 0** |
| 堤防・ダムの決壊 | 0 |
| 最終的な施設 | 取水4 浄水2 配水池2 水道管104 住宅264 水田303 畑3 堤防44 排水機場1 **ダム6径間** |

達成状況6項目 (町の規模・財政・利水・食料・治水・決壊なし) をすべて満たしている。

施設の南北分布が、地形の区分がそのまま効いていることを示している:

| | 40% | 50% | 60% | 70% | 80% |
|---|---|---|---|---|---|
| ダム | **6** | · | · | · | · |
| 取水・浄水・配水池 | · | · | **8** | · | · |
| 住宅 | · | 3 | 139 | 117 | 5 |
| 水田 | · | 62 | 131 | 107 | 3 |
| 堤防 | · | · | 38 | 6 | · |

**ダムは山地の出口 (40%)、町は平野 (50〜80%)** に分かれた。南北を区分する前は、
ダムも町も南 80〜90% に固まっていて、マップの上流 60% がまったく使われていなかった。

洪水が実際に町へ届くようになったのも大きい (浸水した建物 最大5・氾濫原の農地を19失う)。
以前は洪水が峡谷の底で深くなるだけで、治水がほぼ不要だった。

#### 立ち上げ期の建設地 — 「浸水履歴」だけでは足りない

自動プレイは当初、建設地の安全性を **`floodMax` (既往最高水位) だけ**で見ていた。
起動直後は履歴が空なので、これは実質「いま水に浸かっていなければ建ててよい」と
同じことになる。平野を氾濫原として彫ったあと、これで実際に破綻した:

| | 修正前 | 修正後 |
|---|---|---|
| 町の起点の標高 | 2.8m (氾濫原のど真ん中) | 5.1m |
| 40日後の人口 | **5 人** (住宅8棟が水没) | **311 人** |
| 最低資金 | **-2,852** (破産) | +2,529 |

そこで、履歴が無い段階でも**平常時の川の水面から 1.2m の余裕高**を要求するようにした。
標高の絶対値で足切りする方法 (以前の `height < 2`) は、地形の起伏を変えると効かなく
なるので使わない。町の起点選びも「平地が広いこと」ではなく「**水面より高い**平地が
広いこと」で評価する — 氾濫原のど真ん中がいちばん広くて平らなので、そうしないと
必ずそこへ引き寄せられる。

### ダムは本当に効いているのか (`npm run dam-effect`)

「ダムを建てた」だけでは治水になっていない可能性があるので、同じ洪水を
**ダムあり / ダムあり(ゲート操作なし) / ダムなし** の3通りで流して比較する。

ゲート操作は *来る前に空け、来たら閉める*。事前放流は貯水池で受けきれない規模
(150 m³/s 超) のときだけ行う — 中規模の出水にまで事前放流すると、貯めた水を
先に流してしまってかえってピークが上がることが実測でわかった。

> **未解決**: 同梱サンプルのダム (6 径間 @ (64,95)) は、この比較で**まったく差を出せていない**。
>
> ツール側の位置判定は正しい — ダムは町の 46 セル上流、取水点の流域の 36% を押さえており、
> 「洪水調節に効く位置」と判定される。にもかかわらず、ダムあり / なしで
> **マップ全体の水量が 147万 m³ 中 6〜11 m³ (0.0007%) しか変わらない**。
>
> 原因を絞り込んだ結果:
>
> - ダムの列 (y=95) を南へ抜ける流量 7.14 m³/s のうち、**堰を通るぶんは 0.0%**。
>   水は x=35-37 / 85 / 158-159 という別の谷を流れていた。
> - つまりダムは「流れていない溜まり」に架かっている。堰の上流にある水深 1.84m は
>   ダムが貯めたものではなく、元からあった淵。
> - では実流量で適地を選べばよいかというと、そうもいかない。この浅水モデルでは
>   流束が水面勾配に比例するため、**深い淵は流れず、浅い早瀬が水を運ぶ**。
>   水深 1m を超えるセルのうち、意味のある流量があるのは 11% しかない
>   (最大流量のセルは水深 0.03m、最深セル 12.5m の流量は 0.00)。
>   実流量で選ぶよう変えて試したところ、適地が 1 つも見つからなくなった。
>
> **この性質は南北の区分を入れる前の地形でも同じ**なので、区分による退行ではない
> (旧地形でも最深セルの流量は 0.00、最大流量セルの水深は 0.04m)。
> ダムの適地判定を `flowAcc` でも水深でも実流量でもない何かで行う必要がある、
> というところまでが現状。
>
> (この地形を作る前、谷が広かった頃のサンプルでは 21 径間のダムが
> 下流のピーク水位を 1.95m → 0.91m、**53% 低減**していた)

この検証で見つかって直したもの:

- **経済が構造的に破綻していた** — 人口96人の税収 ￥369/日 に対し上水道の維持費だけで ￥1,097/日。
  どう遊んでも赤字から抜け出せなかったので、税収・維持費・作物の収量を組み直した。
- **正常な放流でダムが壊れていた** — 越流判定を「水深」で見ていたため、ゲートを開けて放流している水を
  越流と誤判定していた。「全閉時の天端を水面が越えたか」で判定するよう修正。
- **ダムが満水でも貯め続けて決壊していた** — 上流水位を見て容量が尽きたら全開にする操作を追加。
- **ダムが治水にまったく効いていなかった** — 「上流で流量が大きい所」を探していたため、
  町とは別の水系にダムを架けていた (下流経路が町から136セル離れていた)。
  取水口から本流を遡って地点を選ぶよう修正。あわせて次の3つも直した:
  町を集水域のない枝沢に作っていた / 資金切れで21径間中9径間しか架からず水が素通しだった /
  ダムの水没予定地に自分で田畑を作って沈めていた。
- **ゲート操作が逆効果だった** — 「出水予報が出ている間は全開」にしていたため、
  洪水の最中もゲートが開きっぱなしでダムが何も貯めていなかった。
  *来る前に空け、来たら閉める* 順序に修正し、事前放流は貯水池で受けきれない
  規模 (150 m³/s 超) のときだけ行うようにした。

## セーブ / ロード

`src/sim/save.ts`。地形は seed から決定論的に再生成できるので、保存するのは差分だけ:

- 掘削・盛土で変えたセルだけの標高
- 建造物 (種類・座標・健全度・ゲート開度・生育度・入居率・貯水量)
- 水深・土壌水分・浸水履歴のグリッド (Uint16 / Uint8 に量子化して base64)
- 気象の内部状態 (流域の 2 段貯留槽) — これを復元しないと洪水・渇水の位相がずれる
- 資金・食料と、資金無制限モードの有無 (古いセーブにはこの項目がないので、無い場合は通常モード)

読み込み時、同じ流域なら地形生成を飛ばして即座に差し替え、別の流域なら
地形から作り直して描画側も入れ替える。

同梱のサンプル (`public/saves/sample.json`, 275KB) は上の自動プレイの最終状態。

## 遊び方

| 操作 | |
|---|---|
| 左ドラッグ | 選択中のツールを適用 |
| 右ドラッグ | 地図を移動 (掴んだ地面がカーソルについてくる) |
| W A S D / 矢印キー | 地図を移動 (押している間ずっと) |
| 中ドラッグ / Shift+ドラッグ / Shift+方向キー | 視点を回す (方位・俯角) |
| ホイール / PageUp・PageDown | ズーム (ホイールはカーソルの地点へ寄る) |
| R | 視点をリセット |
| Space | 一時停止 |
| 1 / 2 / 3 / 4 | 速度 |
| Q | 調査モード |
| X / Delete | 撤去ツール (施設を選んでいるならそれを直接撤去) |
| M / H / E / N | 湿潤 / 浸水履歴 / 標高 / 水道網 の表示切替 |
| F / G | 流線 / 格子 |
| Escape | 選択・パネルを閉じて調査モードに戻る |
| 保存 / 読込 | ブラウザ (localStorage) に現在の状態を保存・復元 |
| サンプル | 自動プレイヤーが育てた町を読み込む |
| 画質 | 描画品質・高低差の強調・影・樹木・時刻連動の日照を切り替える |
| 天気 | 手動天気に切り替え、降水強度・天気・気温を自由に指定する |
| ルール | 資金無制限モードの切り替え / 流域のシードの確認・指定・ランダム生成 |

**置いたものを撤去する**

- ツールバー上部「操作」の**撤去 (×)** を選び、消したい施設をクリック。ドラッグすれば
  水道管や堤防をまとめて撤去できる。**X キー**でも同じツールに切り替わる。
- **調査 (?)** で施設をクリックすると右にパネルが出る。その一番下の
  **「この施設を撤去」**ボタンからも消せる (選択中に X / Delete でも同じ)。
- 建設費の 25% が戻る (健全度に比例するので、傷んだ施設ほど戻りは少ない)。
- 掘削・盛土で変えた地面は撤去では戻らない。**盛土**と**掘削**を逆に使って高さを戻す。

**流域を作り直す**

右下の**ルール**に、いまの流域のシードが出ている。入力欄に別のシード (数字でも文字列でもよい)
を入れて**作る**、または**ランダムな流域を作る**で、その場で別の地形に切り替えられる。
地形生成は決定論的なので、同じシードなら必ず同じ流域が出る。選んだシードは URL にも
書き戻されるため、リロードやブックマークでも同じ流域に戻れる。

作り直すと**いまの町は失われる** (建てたものがあるときだけ確認が出る)。資金無制限モードの
設定は流域をまたいで引き継がれる。

**資金無制限モード**

右下の**ルール**から切り替える。建設費・維持費で資金が減らなくなり (資金表示は `￥∞`)、
治水の設計だけを試せる。水の挙動は何も変わらないので、洪水の難しさはそのまま。
設定はセーブデータにも記録され、解除すればそのときの残高から通常モードに戻る。

**序盤の進め方**

1. 川沿いに**取水施設**、隣に**浄水場**と**配水池**。
2. **水道管**でつなぎ、その先に**住宅**。つながっていないと給水されない (調査モードで確認できる)。
3. 川沿いの低地に**水田**、少し離れた場所に**畑**。湿潤オーバーレイ (M) で
   緑 = 水田可 / 黄 = 畑可 が分かる。
4. 梅雨・台風の前に**堤防**を築き、**ダム**で洪水調節。予報を見て**事前放流**でダムを空けておく。
5. 渇水期はダムを閉じて貯留し、取水を守る。

## テストが押さえていること

- 窪地除去後にマップ内から窪地が消え、標高が下がらないこと
- 盆地に入れた水が**質量を保ったまま水平になる**こと、急斜面でも水深が負や NaN にならないこと
- 壁が水を堰き止め、水位が天端を越えれば越流すること
- 生成した流域で川が海まで抜け、水が溜まり続けないこと
- 灌漑が距離で減衰し、**崖の上には届かない**こと / 水路を掘れば届くようになること
- 予報した日の天気が、その日になっても一致すること
- 上水道をつなぐと給水され人口が増え、取水施設と配水池を失うと人口が減ること
- 越流した堤防が損傷し、やがて決壊すること
- ダムのゲートを閉じると上流に貯まり、開けると下流へ放流されること
- 資金無制限モードで、資金 0 でも建設でき、建設費・維持費・返金のどれでも残高が動かないこと
- 横移動でカメラが細かい凹凸に揺すられず、それでいて大きな起伏には乗ること
- ボクセル格子への丸めが冪等・単調で、ずれがブロック高の半分を超えず、
  **GLSL 側の式と負の標高まで一致する**こと (ずれると木や建物がブロックから浮く)
- 目地の間隔が、高さ強調をどこに振ってもブロックを立方体から √2 倍以上ずらさず、
  かつセルの一辺を割り切ること
- ブロックのジオメトリがセル境界の面を1枚ずつしか張らず、外周がジオラマの側面になること
- 実地形で、丸め上がったブロックに水が埋もれず、水際に壁が立ち、
  水中どうしの境界では壁が潰れること
- 保存 → 読み込みで施設・地形改変・資金・日時が戻り、水の分布が誤差 1mm 以内で復元されること
- 資金無制限モードの設定が保存・復元され、設定のない古いセーブは通常モードで読まれること
- 読み込んだ状態から続きをシミュレートしても、元の世界と同じ経過をたどること
- 同梱のサンプルセーブが実際に読み込めて、人口と給水が生きていること
- 自動プレイヤーが 40 日で上水道を敷き、人口を増やし、破産も建物の損失もしないこと
